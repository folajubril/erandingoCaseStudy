Availability Screen

Single large toggle: ONLINE / OFFLINE. Fullscreen tap-target. Status badge always visible in header. No deep menus. Tap → confirmation toast → backend PATCH update. Offline = stops receiving orders immediately.

Incoming Order Screen

Full-screen modal with loud sound + vibration. Shows: pickup address, drop-off address, estimated pay, package type. Two large buttons: ACCEPT (green) / DECLINE (red). 30-second auto-expire timer with count-down. Auto-declines and flags to ops if no action.

Active Delivery Screen

Current step highlighted (PICKUP ▸ IN TRANSIT ▸ DELIVERED). Address + contact shown. One action button at a time: "I'm at Pickup" → "Mark Picked Up" → "Mark Delivered". Minimal scrolling. Works offline — queues confirmations.

Real-Time Update Strategy

Primary: WebSocket (Socket.io)

Persistent connection when app is foreground. Server emits order events to rider's socket room. Instant updates — no polling overhead. Reconnects automatically on disconnect with exponential backoff.

Fallback: FCM Push + Short Poll

When app is background/killed → FCM push notification wakes app. On foreground restore: single REST call to sync latest order state. Short-poll (10s) only when WebSocket is confirmed dead — avoids battery drain.

Failure Handling

Failure Detection Response
No Network NetInfo API monitors connectivity Offline banner shown. Status updates queued locally (AsyncStorage). Auto-sync when reconnected. Order state readable from local cache.
App Crash / Kill Backend tracks last heartbeat per rider Active order state preserved on backend. On next app open: resume screen shown with current order. No duplicate assignment — backend is source of truth.
Duplicate Orders Idempotency key on every status update Each action (Accept, Picked Up, Delivered) uses a unique key. Backend rejects duplicates with 409. App ignores duplicate errors — treats as success.
Order Accept Race Optimistic lock on order record First rider to commit wins. Others get "Order no longer available" toast and return to AVAILABLE state.

Order Lifecycle — Data Flow

1. Order Created

Customer messages WhatsApp → Timi AI parses → POST /orders → record created (status: PENDING) → Socket.io emits order.new to Admin room + nearest available rider's room.

2. Rider Assigned

Ops selects rider in Admin → PATCH /orders/:id/assign → DB updated (status: ASSIGNED, rider_id set) → FCM push + Socket event sent to rider. Admin table updates in real-time.

3. Rider Accepts

Rider taps Accept → PATCH /orders/:id/status {status: ACCEPTED} with idempotency key → DB locked → status: ASSIGNED confirmed → both Admin + other systems notified.

4. In Transit

Rider taps "Mark Picked Up" → PATCH status: IN_TRANSIT → timestamp recorded → Admin row updates colour. Customer notified on WhatsApp automatically via webhook.

5. Completed

Rider taps "Mark Delivered" → PATCH status: COMPLETED → timestamps, rider earnings log updated → Socket event closes tracking. WhatsApp delivery confirmation sent to customer.

API Design — Key Endpoints

// Orders POST /api/orders — create order (WhatsApp webhook → Timi) GET /api/orders — list with filters (status, zone, date) GET /api/orders/:id — order detail + timeline PATCH /api/orders/:id/status — rider status update (idempotency-key header) PATCH /api/orders/:id/assign — admin reassign rider DELETE /api/orders/:id — cancel with reason // Riders GET /api/riders — list with status, zone PATCH /api/riders/me/status — toggle availability POST /api/riders/me/heartbeat — 30s keep-alive ping // Escalations POST /api/escalations — create issue report PATCH /api/escalations/:id/resolve — admin resolves

Consistency Strategy

Backend = Single Source of Truth

All status changes go through the API — never directly from app to app. Mobile and Admin are read+write clients. On reconnect, both fetch latest state from REST before resuming WebSocket sync.

Idempotency + Optimistic Locking

Every mutation includes an idempotency key. Order state transitions validated server-side (cannot go COMPLETED → IN_TRANSIT). Audit log records every change with actor, timestamp, and previous state.

Section 5

Performance & Reliability

Diagnosing slow apps, lagging dashboards, and delayed orders.
Mobile Bottlenecks
  • Large JS bundle → slow cold start
  • Unoptimised images (no WebP)
  • Re-renders on every socket event
  • Blocking API calls on main thread
  • No local caching → every open = re-fetch
API Bottlenecks
  • No DB indexes on order status/rider_id
  • N+1 queries in order list endpoint
  • Synchronous WhatsApp webhook processing
  • No query result caching (Redis)
  • Too many WebSocket broadcasts (no rooms)
Dashboard Bottlenecks
  • Full table re-render on any socket event
  • Fetching all orders (no pagination)
  • Heavy charting library loaded on first paint
  • No skeleton loaders → perceived slowness
  • Admin state not persisted across refreshes

Diagnosis Approach

Layer Tool What I Check
Mobile Expo DevTools + Flipper JS bundle size, render counts, API response times, network calls
Backend Datadog / Sentry + EXPLAIN ANALYZE Slow queries, error rates, endpoint latency, socket connection count
Database pg_stat_statements Missing indexes, sequential scans on large tables, lock contention
Dashboard Chrome DevTools Perf tab Long tasks, layout thrashing, unnecessary re-renders (React DevTools)

Optimisation Priority (Impact vs Effort)

First — DB Indexes

Add indexes on orders(status, created_at, rider_id). Fastest win — zero code changes, massive query improvement.

Second — API Pagination

Limit all list endpoints to 50 records + cursor pagination. Prevents admin from loading 10,000 orders into a table.

Third — Redis Caching

Cache rider list and active orders for 5 seconds. Reduces database load by 80% during peak ops.

Fourth — Mobile Code Splitting

Lazy-load Manager screens. Errandian flow loads first. Reduces initial bundle by ~30%.

Fifth — Targeted Socket Rooms

Emit events only to the relevant rider's room, not all connections. Eliminate broadcast noise.

Scope Creep Scenario

Founder requests advanced analytics + rider heatmaps pre-launch. Engineering flags delay risk.
My Response to Founder

I acknowledge the value of heatmaps and analytics — they are genuinely useful for operations at scale. However, building them before launch risks delaying the core system that makes them meaningful.

I'd say: "Let's collect the data from day one, so we can build the analytics on top of real operational data after launch — not dummy data."

What I Push Back On
  • Building a heatmap before we have a single live order
  • Complex charting dashboards blocking rider app completion
  • Real-time analytics infrastructure (Kafka, ClickHouse) pre-MVP
  • Any feature that shares engineers with the critical path
What I Ship Instead (Now)
  • Basic daily counters on the admin home screen (orders, completions, failures)
  • CSV export endpoint — ops can analyse in Google Sheets
  • All raw events stored (orders table with full timestamps) for future analytics
What I Defer (Post-Launch)
  • Rider heatmaps using real GPS/zone data from live orders
  • Performance charts (order volume, completion rate trends)
  • Automated SLA alerts
  • Exportable PDF reports
Delivery Protection Principle I protect the launch date by ring-fencing the critical path. Any new request gets assessed: does this block delivery? If yes → defer. If not → lightweight version only. The goal is to launch with a working core, then iterate with real data.
Section 7

Failure Scenario — Real-Time Ops (Launch Day)

Orders not showing on rider app · Admin shows inconsistent data · Support overwhelmed.
Step 1 — Check What's Alive

Immediately open the monitoring dashboard (Datadog / Sentry). Check: Is the API server up? Is the database reachable? Are WebSocket connections dropping? What does the error rate graph look like in the last 15 minutes?

Step 2 — Isolate the Layer

Test REST directly: Hit GET /api/orders via Postman — if it returns correct data, backend DB is fine.
Test WebSocket: Connect a test client — if events aren't flowing, the socket gateway or Redis pub/sub is the issue.
Test Mobile specifically: Check if FCM tokens are registered. Check if the app is connected to the right environment (prod vs staging URL).

Step 3 — Common Culprits to Check

Redis connection pool exhausted (WebSocket state breaks) · Database connection limit hit under load · WhatsApp webhook routing broken (orders not created) · Wrong API base URL in production build · Missing environment variable in prod deployment.

Step 4 — Temporary Stabilisation

Disable WebSocket: Switch mobile app to 10-second polling mode via a feature flag. Slower, but reliable.
Ops workaround: Give ops team direct DB read access or a simple internal admin query page for order lookup while real-time is broken.
WhatsApp fallback: Have Timi send customers a manual "order received" message while routing is investigated.

Step 5 — Restore + Post-Mortem

Once root cause identified: apply fix, deploy, verify with smoke tests. Document the failure timeline. Add alerting thresholds (e.g., alert if zero orders processed in 5 minutes). Add health check endpoint polled every 60s.

WhatsApp-first + Mobile + Web Strategy

Three-layer architecture: Customer (WhatsApp) → Execution (Mobile) → Control (Web).
💬 WhatsApp — Customer Layer
  • Zero-install. Customer is already on WhatsApp
  • Timi AI handles order intake via NLP
  • Automated status updates to customer
  • Human handoff for edge cases
Low frictionHigh reach
Risks
  • WhatsApp API rate limits + policy changes out of our control
  • Timi misparse → wrong order details → ops overhead
  • Limited UI makes complex orders (multi-stop) hard to capture
📱 Mobile — Execution Layer
  • Errandians manage full order lifecycle
  • Managers oversee their zone in real-time
  • Works offline + low-end devices
  • Push notifications for instant alerting
Risks
  • Rider must install and keep app updated
  • Low-end Android fragmentation causes inconsistent behaviour
  • Background kill on budget phones breaks push delivery
🖥 Web — Control Layer
  • HQ has full visibility + override capability
  • Complex actions (reassign, cancel, escalate)
  • Historical data and reporting
  • No device install constraint
Risks
  • Browser tab-close breaks WebSocket — requires reconnect logic
  • Ops dependency — if dashboard is down, ops team is blind
  • Real-time state divergence if ops has stale tab open

Scaling Challenges & When Architecture Must Evolve

Challenge Trigger Point Evolution
WebSocket connections > 500 concurrent riders Move to Redis cluster + socket.io sticky sessions / migrate to managed WS service
WhatsApp rate limits > 1,000 msgs/day Implement message queue (Bull/BullMQ) with retry logic
Order volume > 10k orders/day Introduce read replicas for admin queries; separate write/read DB paths
Multi-city expansion 2nd city launch Zone-based architecture; orders scoped to zone; separate socket rooms per city
Timi AI complexity Ambiguous orders increase Add structured conversation flows + human-in-the-loop escalation path
